# ![cluster-eck](https://helm-repository.readthedocs.io/en/latest/img/cluster-eck.svg "Cluster Chart : Elasticsearch") Cluster Chart : Elasticsearch
[![Artifacthub](https://img.shields.io/badge/ArtifactHub-STARTX_cluster--eck-8A2BE2.svg)](https://artifacthub.io/packages/search?ts_query_web=cluster+eck+startx)

Configure the Elastic Cloud on Kubernetes (ECK) operator and the Elasticsearch clusters and Kibana instances it manages.

This chart is part of the [cluster-xxx startx helm chart series](https://helm-repository.readthedocs.io#cluster-helm-charts) that doesn't necessarily deploy pods but rather represent a cluster configuration state orchestrated by gitops tools like ArgoCD.

This chart installs the certified `elasticsearch-eck-operator-certified` operator of Elastic and manages:

- the **Elasticsearch clusters** (`Elasticsearch` CR): version, node sets, configuration, resources and volumes, with an optional route
- the **Kibana instances** (`Kibana` CR) connected to these clusters, with an optional route
- the **kernel setting** required by Elasticsearch on the nodes (`Tuned` CR of the Node Tuning Operator)
- the **secrets** referenced by these resources (secure settings, users, certificates), from values or through an `ExternalSecret`

The other resources of the operator (Elastic Agent, Beats, Logstash, APM Server...) are not managed by this chart.

## Requirements and guidelines

Read the [startx helm-repository homepage](https://helm-repository.readthedocs.io) for
more information on how to use these resources.

### Prerequisites

- Access to the `certified-operators` catalog of the software catalog
- `cluster-admin` privileges
- A storage class for the data volumes of Elasticsearch (the default one unless `storageClassName` is set)
- The Elastic resources must be created in a regular namespace: never `default`, `kube-*` or `openshift-*`, where the security
  context constraints are not applied as Elasticsearch expects
- The namespace must be attached to the default pod network. The operator manages Elasticsearch and Kibana through their HTTP
  services: a namespace attached to a primary user-defined network isolates them from the operator

The operator is installed in the `openshift-operators` namespace (AllNamespaces mode), so no dedicated OperatorGroup is created.
The Elasticsearch clusters and the Kibana instances run in the `default-eck` namespace created by the `project` sub-chart, with the
`restricted-v2` security context constraint of OpenShift: no privileged init container is used, and the Elasticsearch plugins
cannot be installed at runtime (build a custom image instead).

### Virtual memory of the nodes

Elasticsearch maps its indices in memory and needs a high `vm.max_map_count` kernel setting on the nodes it runs on:

- OpenShift nodes set `vm.max_map_count` to `262144` with their default tuning profile
- Elastic recommends `1048576` in production for Elasticsearch 8.16 and later

The `tuned` block creates a `Tuned` resource raising this setting on the selected nodes, without reboot. Select the nodes running
Elasticsearch with `tuned.match`, and extend the profile these nodes already use with `tuned.include`: `openshift-node` for the
worker nodes, `openshift-control-plane` for the infra and control plane nodes. For a demonstration, `node.store.allow_mmap: false`
in the configuration of a node set avoids the requirement, at the cost of the performance.

### Objects created by the operator

| Object                            | Name                          | Content                                                         |
| --------------------------------- | ----------------------------- | --------------------------------------------------------------- |
| Service of the Elasticsearch API  | `<name>-es-http`              | Port `9200`, HTTPS with a certificate generated by the operator |
| Secret of the `elastic` user      | `<name>-es-elastic-user`      | Key `elastic`: password of the built-in superuser               |
| Secret of the public certificates | `<name>-es-http-certs-public` | Certificate authority to trust when calling the API             |
| Service of Kibana                 | `<name>-kb-http`              | Port `5601`, HTTPS                                              |

```bash
oc -n default-eck get secret <name>-es-elastic-user -o go-template='{{.data.elastic | base64decode}}'
```

A route created by this chart (`route.enabled`) uses the `passthrough` termination by default: Elasticsearch or Kibana presents its
own certificate, self-signed by the operator unless `spec.http.tls.certificate` references a tls secret. Elasticsearch can also be
exposed with a service of type `LoadBalancer` (`spec.http.service.spec.type`), for example with the
[cluster-metallb](https://helm-repository.readthedocs.io/en/latest/charts/cluster-metallb) chart.

## Deploy this helm chart on openshift

### 1. Connect to your Openshift cluster

```bash
oc login -t <token> <cluster-url>
```

### 2. Install the repository

```bash
helm repo add startx https://helm-repository.readthedocs.io/en/latest/repos/stable/
```

### 3. Get information about this chart

```bash
helm show chart startx/cluster-eck
```

### 4. Install this chart

#### Default values

The default values keep every feature disabled and render nothing: the Elasticsearch clusters are specific to each environment
and must be provided in a values file.

- No Elasticsearch cluster, no Kibana instance and no node tuning are created
- The operator subscription and namespace are managed separately via the `operator` and `project` sub-charts (both disabled by default)

```bash
# base configuration running default configuration
helm install cluster-eck startx/cluster-eck
```

#### Full deployment with operator and project

Helm cannot create a custom resource before its API exists: install the namespace and the operator first, approve its
InstallPlan (the subscription uses `installPlanApproval: Manual`), then enable the node tuning, an Elasticsearch cluster and Kibana.

```bash
# 1. namespace and operator
helm install cluster-eck startx/cluster-eck \
  --set project.enabled=true \
  --set operator.enabled=true
oc -n openshift-operators get installplan
oc -n openshift-operators patch installplan <name> --type merge -p '{"spec":{"approved":true}}'

# 2. node tuning, Elasticsearch cluster and Kibana, once the operator is running
cat > my-eck.yaml <<EOF
tuned:
  enabled: true
elasticsearch:
  enabled: true
  list:
    - name: default
      spec:
        version: 9.5.0
        nodeSets:
          - name: default
            count: 3
            podTemplate:
              spec:
                containers:
                  - name: elasticsearch
                    resources:
                      requests:
                        cpu: "1"
                        memory: 4Gi
                      limits:
                        memory: 4Gi
            volumeClaimTemplates:
              - metadata:
                  name: elasticsearch-data
                spec:
                  accessModes:
                    - ReadWriteOnce
                  resources:
                    requests:
                      storage: 50Gi
kibana:
  enabled: true
  list:
    - name: default
      route:
        enabled: true
      spec:
        version: 9.5.0
        count: 1
        elasticsearchRef:
          name: default
EOF
helm upgrade cluster-eck startx/cluster-eck -f my-eck.yaml \
  --set project.enabled=true \
  --set operator.enabled=true
```

Follow the deployment with `oc -n default-eck get elasticsearch,kibana`: the cluster is ready when its health is `green`.

## Deploy with ArgoCD

### Deploy via ArgoCD Application

Deploy `cluster-eck` using three dedicated ArgoCD Applications - one per concern - all sharing the same AppProject:

```bash
git clone https://gitlab.com/startx1/helm.git
cd helm-repository/charts/cluster-eck/examples/argocd/
oc apply -k .
```

| Application            | Wave   | Enabled flags                                                                 | Destination           |
| ---------------------- | ------ | ----------------------------------------------------------------------------- | --------------------- |
| `cluster-eck-project`  | `"1"`  | `project.enabled: true`, all others `false`                                   | `default-eck`         |
| `cluster-eck-operator` | `"5"`  | `operator.enabled: true` (`operatorGroup.enabled: false`), all others `false` | `openshift-operators` |
| `cluster-eck-app`      | `"10"` | `tuned`, `elasticsearch` and `kibana` `enabled: true`, all others `false`     | `default-eck`         |

The automated sync policy ensures ArgoCD reconciles each concern independently whenever the chart or values drift from the desired state.
The `cluster-eck-app` Application also creates the `Tuned` resource in the `openshift-cluster-node-tuning-operator` namespace, the
only one where the Node Tuning Operator reads it. The Subscription uses `installPlanApproval: Manual`: the `cluster-eck-app`
Application stays out of sync until the InstallPlan of the operator is approved (`SkipDryRunOnMissingResource=true` lets the sync
start before the Elastic APIs exist).

## External secrets

The secrets of the `secrets` block (secure settings of a snapshot repository, users of the file realm, certificates) can come from
an external store (Vault, AWS Secrets Manager...) through the [External Secrets Operator](https://external-secrets.io) instead of
the chart values. With `externalSecret.enabled: true`, the chart renders an `ExternalSecret` producing the Secret of the same name,
namespace and type, so the Elastic resource referencing it is unchanged. Without `externalSecret`, the chart renders the Secret
from `data`. Never commit a real credential in a values file.

```yaml
externalSecretDefaults:
  secretStoreRef:
    name: vault-backend
    kind: ClusterSecretStore
secrets:
  enabled: true
  list:
    - name: es-snapshot-s3
      externalSecret:
        enabled: true
        remoteRefs:
          s3.client.default.access_key:
            key: ocp/eck/snapshot-s3
            property: access_key
          s3.client.default.secret_key:
            key: ocp/eck/snapshot-s3
            property: secret_key
elasticsearch:
  enabled: true
  list:
    - name: default
      spec:
        version: 9.5.0
        secureSettings:
          - secretName: es-snapshot-s3
        nodeSets:
          - name: default
            count: 3
```

An `externalSecret` block accepts `secretStoreRef` and `refreshInterval` (defaults: `externalSecretDefaults`),
`remoteRefs` (map of secret key to ESO `remoteRef`) and the raw ESO fields `data`, `dataFrom` and `template`.
Rendering fails when no store is set or when no key source is provided.
