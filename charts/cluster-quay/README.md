# ![cluster-quay](https://helm-repository.readthedocs.io/en/latest/img/cluster-quay.svg "Cluster Chart : Quay") Cluster Chart : Quay
[![Artifacthub](https://img.shields.io/badge/ArtifactHub-STARTX_cluster--quay-8A2BE2.svg)](https://artifacthub.io/packages/search?ts_query_web=cluster+quay+startx)

This helm chart is used to create an operator based deployment of the Red Hat Quay registry, from the single pod
databases generated by the operator (default values, the behaviour of the previous releases) up to a highly available
registry: configuration bundle rendered by the chart, external S3 object storage, PostgreSQL clusters of Quay and
Clair managed by the [cluster-crunchy](https://helm-repository.readthedocs.io/en/latest/charts/cluster-crunchy),
[cluster-cloudnativedb](https://helm-repository.readthedocs.io/en/latest/charts/cluster-cloudnativedb) or
[cluster-percona](https://helm-repository.readthedocs.io/en/latest/charts/cluster-percona) sub-chart
(several instances, synchronous replication, S3 backups, point in time restore, monitoring, network policies) or
operated elsewhere, OIDC login, pod disruption budgets, Argo CD Vault Plugin placeholders for every secret.

This chart is part of the [cluster-xxx startx helm chart series](https://helm-repository.readthedocs.io#cluster-helm-charts) that doesn't necessarily deploy pods but rather represent a cluster configuration state orchestrated by gitops tools like ArgoCD.

## Requirements and guidelines

Read the [startx helm-repository homepage](https://helm-repository.readthedocs.io) for
more information on how to use these resources.

| Requirement | Detail |
| --- | --- |
| OpenShift 4.17+ (Kubernetes 1.30+) | `kubeVersion` of the chart |
| Red Hat Quay 3.18 | Quay operator from `redhat-operators`, channel `stable-3.18`, installed by the `operator` sub-chart. Cluster wide (`openshift-operators`) when `quay.components.monitoring` is managed: the monitoring component requires the AllNamespaces mode |
| `database.mode: crunchy` | Crunchy Postgres for Kubernetes 5.8 (`certified-operators`, package `crunchy-postgres-operator`), installed and configured by the `crunchy` sub-chart ([cluster-crunchy](https://helm-repository.readthedocs.io/en/latest/charts/cluster-crunchy)). Support subscription required in production for organizations of 50 employees or more |
| `database.mode: cloudnativedb` | CloudNativePG 1.30 (community build certified by EDB, package `cloudnative-pg`, Apache 2.0) or EDB Postgres for Kubernetes (`flavor: edb`, EDB subscription), installed and configured by the `cloudnativedb` sub-chart ([cluster-cloudnativedb](https://helm-repository.readthedocs.io/en/latest/charts/cluster-cloudnativedb)) |
| `database.mode: percona` | Percona Operator for PostgreSQL 3.1 (`certified-operators`, package `percona-postgresql-operator-certified`, Apache 2.0, built on the Crunchy PGO engine), installed and configured by the `percona` sub-chart ([cluster-percona](https://helm-repository.readthedocs.io/en/latest/charts/cluster-percona)) |
| `storage.mode: external` | An S3 compatible bucket (Ceph RGW, MinIO, NooBaa, Amazon S3...) with its credentials |
| `storage.mode: operator` | OpenShift Data Foundation (NooBaa): the operator creates an ObjectBucketClaim |
| Backups of the databases | A second S3 bucket reachable from the database pods (`crunchy.s3.list`, `cloudnativedb.s3.list`, `percona.s3.list`) |
| Secrets | Passwords, keys and credentials are expected as [Argo CD Vault Plugin](https://argocd-vault-plugin.readthedocs.io/) placeholders (`<path:kv/data/...#key>`) or supplied by a values file kept out of Git; the chart never generates them |

## What the chart renders

| Object | Namespace | Condition |
| --- | --- | --- |
| `Namespace` of the registry (sub-chart `project`) | | `project.enabled` |
| `Subscription` and `OperatorGroup` of the Quay operator (sub-chart `operator`), of the Container Security operator (sub-chart `operatorsec`) | `operator.subscription.namespace` | `operator.enabled`, `operatorsec.enabled` |
| `Secret <app>-pull-auth` (registry.redhat.io credentials), `Secret <app>-adminuser`, legacy `Route` and `Service` | registry | `rhn.enabled`, `quay.admin.enabled`, `route.enabled` |
| `QuayRegistry` | registry | `quay.enabled` |
| `Secret <name>-config-bundle` (`config.yaml`, `clair-config.yaml`, `extra_ca_cert_*`, `ssl.cert/key`) | registry | `quay.enabled` and `quay.config.enabled` without `quay.config.existingSecret` |
| `Secret postgresql-client-certs` (`ca.crt`, projected by the operator in `/run/secrets/postgresql`) | registry | `database.tls.mode: verify-full` (also with an existing config bundle) |
| `PodDisruptionBudget` quay-app, clair-app, quay-mirror (`maxUnavailable: 1`) | registry | `quay.enabled` and `quay.podDisruptionBudgets.enabled` |
| `Namespace`, `OperatorGroup` and `Subscription` of the database operator, `PostgresCluster`, `Cluster` or `PerconaPGCluster` quay-db and clair-db, their Secrets, backups, monitoring and `NetworkPolicy` | databases | `crunchy.enabled`, `cloudnativedb.enabled` or `percona.enabled`, with the flags of the sub-chart (`project.enabled`, `operator.enabled`, `cluster.enabled`) |

"registry" is `project.project.name` (`quay-operator` by default, `quay-enterprise` in the HA values files), "databases" the namespace of the sub-chart entries
(`crunchy.cluster.list[].namespace`). Argo CD sync waves order the objects: namespaces (-10), OperatorGroup (-6),
Subscriptions (-5), Secrets and ConfigMaps (1), database clusters and network policies (15), `QuayRegistry` (25),
budgets, scheduled backups and alerts (30).

## Deploy this helm chart on openshift

### 1. Connect to your Openshift cluster

```bash
oc login -t <token> <cluster-url>
```

### 2. Install the repository

```bash
helm repo add startx https://helm-repository.readthedocs.io/en/latest/repos/stable/
```

### 3. Get information about this chart

```bash
helm show chart startx/cluster-quay
helm show values startx/cluster-quay
```

### 4. Install this chart

```bash
helm install cluster-quay startx/cluster-quay
```

Highly available registry with Crunchy databases, every secret in a values file kept out of Git (the chart refuses to
render while a required value is missing, `helm template cluster-quay startx/cluster-quay --kube-version 1.33.0
-f values-startx-quay-ha-crunchy.yaml -f my-secrets.yaml --set quay.enabled=true` shows it without a cluster):

```yaml
# my-secrets.yaml: the <path:...> placeholders of values-startx-quay-ha-crunchy.yaml, as values
quay:
  config:
    hostname: quay.apps.ocp.example.com
    secretKey: <64 random characters>
    databaseSecretKey: <64 random characters>
storage:
  external:
    host: s3.example.com
    bucket: quay-registry
    accessKey: <access key>
    secretKey: <secret key>
crunchy:
  s3:
    list:
      - name: quay-backup
        namespace: quay-postgres
        endpoint: s3.example.com
        region: us-east-1
        bucket: quay-pgbackrest
        accessKey: <access key>
        secretKey: <secret key>
  cluster:
    list:
      - name: quay-db
        password: <alphanumeric password>
      - name: clair-db
        password: <alphanumeric password>
```

Lists are replaced, not merged, by Helm: a values file that sets `crunchy.cluster.list` or `crunchy.s3.list` must
carry the complete entries (copy them from `values-startx-quay-ha-crunchy.yaml`).

```bash
V="-f values-startx-quay-ha-crunchy.yaml -f my-secrets.yaml"
# namespaces, then the operators (approve the InstallPlans: installPlanApproval Manual)
helm install cluster-quay-project startx/cluster-quay $V --set project.enabled=true --set crunchy.project.enabled=true
helm install cluster-quay-operator startx/cluster-quay $V --set operator.enabled=true --set crunchy.operator.enabled=true
oc get installplan -A | grep -E 'quay-operator|postgresoperator'
# databases and registry
helm install cluster-quay-app startx/cluster-quay $V --set quay.enabled=true --set crunchy.cluster.enabled=true
```

With `helm install` every object of a release is created at once: the Quay operator retries until the databases
accept connections (a few minutes). Argo CD orders the waves and waits for the databases (see below). Passwords and
keys are written verbatim in `DB_URI` and in the Clair connection strings: use alphanumeric values
(`openssl rand -hex 32`), never URL reserved characters.

## Default values

Complete deployment of a project with the following characteristics :

- 1 **namespace:** named **quay-operator** without constraints
- 1 **operator:** named **quay-operator** configured with
  - The **stable-3.18** channel of the redhat-operators catalog
  - The **v3.18.0** version
  - Deployed under the **openshift-startx-quay** project (subscription and operator group disabled by default)
- 1 **registry:** named after the context application (**default-quay**) configured with
  - every component managed by the operator (single pod PostgreSQL databases, Redis, ObjectBucketClaim storage, Clair, mirroring, HPA, route, TLS, monitoring)
  - the configuration generated by the operator (`quay.config.enabled: false`)
  - the registry.redhat.io pull Secret, the admin user Secret, the legacy route and service

```bash
# Create the project
helm install cluster-quay-project startx/cluster-quay --set project.enabled=true,operator.enabled=false,quay.enabled=false
# Deploy the quay operator
helm install cluster-quay-operator startx/cluster-quay --set project.enabled=false,operator.enabled=true,operator.subscription.enabled=true,operator.operatorGroup.enabled=true,quay.enabled=false && sleep 10
# Configure the registry
helm install cluster-quay-app startx/cluster-quay --set project.enabled=false,operator.enabled=false,quay.enabled=true
```

## Deploy with ArgoCD

### AppProject

```bash
git clone https://gitlab.com/startx1/helm.git
cd helm-repository/charts/cluster-quay/examples/argocd/
oc apply -k .
```

### Applications

The `examples/argocd` folder holds the AppProject and the three Applications (project, operator, app) of the standard
pattern with `values-startx_noinfra-quay.yaml`: the registry of the previous releases, every component managed by the
operator.

### Highly available registry

`examples/argocd-ha` holds the same three Applications for `values-startx_noinfra-quay-ha-crunchy.yaml`
(`values-startx_noinfra-quay-ha-cloudnativedb.yaml` and `values-startx_noinfra-quay-ha-percona.yaml` with the
`cloudnativedb.*` or `percona.*` flags): the project Application
(wave 1, no finalizer) creates the registry and database namespaces (`project.enabled`, `crunchy.project.enabled`),
the operator Application (wave 5) the OLM subscriptions of the Quay operator in `openshift-operators` and of the
Crunchy operator in the database namespace (`operator.enabled`, `crunchy.operator.enabled`), the app Application
(wave 10) the databases, the config bundle, the `QuayRegistry` and the budgets (`quay.enabled`,
`crunchy.cluster.enabled`). Every flag is false in the values file, so that each Application renders its own objects.
Approve the InstallPlans (`installPlanApproval: Manual`) before the app Application syncs.

```bash
oc apply -k examples/argocd-ha/
# health checks of PostgresCluster, CloudNativePG and EDB Cluster, PerconaPGCluster, QuayRegistry, Subscription and Application:
# Argo CD waits for the databases (wave 15) before creating the QuayRegistry (wave 25)
oc patch argocd openshift-gitops -n openshift-gitops --type merge --patch-file examples/argocd-ha/argocd-health.yaml
```

`--patch-file` replaces `spec.resourceHealthChecks`: merge the lists if the ArgoCD resource already has some. On a
vanilla Argo CD, put the same Lua in `argocd-cm` (`resource.customizations.health.<group>_<kind>`). The rules only
read what the operators publish in `.status`: a durable failure (restore failed, volume resize refused, reconciliation
refused by the operator, `RolloutBlocked`, failed migrations) is `Degraded`, so the sync fails and is retried instead of
waiting forever; a status older than the spec (`observedGeneration` behind `metadata.generation`) stays `Progressing`.
Crash-looping database instances are reported by the operators as "not ready", that is `Progressing`: the alerts of the
database charts cover that case. The `postgresql.cnpg.io` rule replaces the one built into Argo CD, which classifies
switchovers and configuration changes as `Degraded`.

### Values in Git, secrets in Vault (ApplicationSet)

`examples/argocd-ha/applicationset.yaml` is one ApplicationSet that generates two Applications (operators, registry)
for every target cluster:

- the chart comes from the STARTX Helm repository (`spec.source.chart`, `targetRevision` = chart version);
- the target clusters are picked by a clusters generator on the label `cluster-quay-ha` (any value) of the cluster
  Secrets registered in Argo CD, set by your automation (with ACM, `GitOpsCluster` copies the ManagedCluster labels
  onto those Secrets: label the ManagedCluster). The Applications are named `cluster-quay-ha-operators-<cluster>` and
  `cluster-quay-ha-<cluster>` and target `{{ .server }}` of the cluster;
- the values file lives in a Git repository named after the cluster (`<cluster>`), file `quay/values.yaml`
  (`examples/argocd-ha/values-example.yaml` is a complete one): the git files generator, interpolated with the cluster
  name, reads it, the template hands it to the plugin as `HELM_VALUES`, and a commit on the file regenerates the
  Applications. An outer matrix with a list generator adds the `--set` flags of `HELM_ARGS` (namespaces and operators
  for the first Application, `quay.enabled` and `crunchy.cluster.enabled` for the second). The first generator of a
  matrix wins on a key conflict: a project scoped cluster Secret (non empty `project` field) would shadow the
  `project` sub-chart values, so register the clusters without a project;
- secrets are Argo CD Vault Plugin placeholders (`secretKey: <path:kv/data/quay/prod#secret_key>`) that
  `helm template` leaves untouched and that the plugin substitutes after rendering; the chart never encodes a
  value, so the placeholders also work inside `DB_URI` and the Clair connection strings. Documentation placeholders
  (`<value>`) left in a non secret value make the rendering fail on purpose;
- `templatePatch` gives the registry Application `prune: true`, `retry` and the `ignoreDifferences` on the
  finalizers added by the operators. Requires Argo CD 2.10+ (OpenShift GitOps 1.12+).

The plugin (`examples/argocd-ha/avp-plugin.yaml`, a Config Management Plugin named `argocd-vault-plugin-helm`) runs
`helm template --kube-version $KUBE_VERSION $HELM_ARGS -f <HELM_VALUES> . | argocd-vault-plugin generate -` in the
chart directory extracted by the repo-server. The sidecar authenticates to Vault with the Kubernetes method
(`AVP_AUTH_TYPE=k8s`): the service account token of the repo-server pod is presented to a Vault role bound to that
service account, with a policy reading the KV path of the placeholders:

```bash
vault auth enable kubernetes      # once; then configure it with the API server address, its CA and a token reviewer
vault policy write quay-prod - <<'EOF'
path "kv/data/quay/prod" { capabilities = ["read"] }
EOF
vault write auth/kubernetes/role/argocd \
  bound_service_account_names=openshift-gitops-repo-server bound_service_account_namespaces=openshift-gitops \
  policies=quay-prod ttl=1h
```

Register the Git repository of each cluster in Argo CD (`examples/argocd-ha/repo-secret.yaml`, a repository Secret
with a read-only deploy token), allow them with a glob and the Helm repository in the AppProject `sourceRepos`, and
any registered cluster for the Quay namespaces in its `destinations` (`examples/argocd-ha/appproject.yaml`), apply the
ApplicationSet, approve the InstallPlans. A value changed in Vault is not seen by the manifest cache:
`argocd app get <application> --hard-refresh` then sync. `argocd app rollback` is refused while automated sync is
on: every change, including a restore, goes through Git. The Secrets carry
`argocd.argoproj.io/sync-options: ServerSideApply=true`, so that no clear text copy lands in a
`last-applied-configuration` annotation.

`examples/argocd-ha/applicationset-single.yaml` generates one Application per cluster that renders the namespaces,
the operators, the databases and the registry together (every flag in `HELM_ARGS`): the sync waves order everything,
the first sync waits at wave -5 until the InstallPlans are approved, the custom resources carry
`SkipDryRunOnMissingResource=true` so that the dry run does not fail while their CRDs are missing, and both namespaces
carry `Prune=false`. What you lose compared with two Applications: the health of the registry and the state of the
operators are one status, and a sync that includes a changed Subscription waits for the InstallPlan approval before
touching anything else.

## Procedures

### First super user

With `quay.config.userInitialize: true` the API creates the first account once (`quay.config.superUsers` must contain it):

```bash
curl -s -X POST https://quay.apps.ocp.example.com/api/v1/user/initialize -H 'Content-Type: application/json' \
  -d '{"username":"quayadmin","password":"<password>","email":"quayadmin@example.com","access_token":true}'
```

Keep the returned `access_token` (API). Then set `quay.config.userInitialize: false` and sync.

### Enable the OIDC login (Keycloak)

1. Keycloak: confidential client `quay`, standard flow, PKCE S256, redirect URIs `https://<hostname>/oauth2/sso/callback`,
   `.../callback/attach`, `.../callback/cli`; *Direct access grants* only when `podman login` with the Keycloak
   password is required (with `internalAuthentication`, Quay then checks passwords through the password grant;
   otherwise users log in with an application token and the CI with robots); for team synchronization, a mapper
   that emits the user's teams as a JSON array under the claim of `groupClaim`, with *Add to userinfo* enabled
   (Quay reads the claims from the userinfo endpoint): a *Group Membership* mapper (claim `groups`, without full
   path) or a *User Attribute* mapper on a multivalued attribute; client scopes `openid`, `email`, `profile`.
2. Add the Keycloak usernames of the administrators to `quay.config.superUsers`, as Quay normalizes them (lower case,
   characters outside `a-z0-9_` replaced by `_`, and a suffix such as `1` when the name is already taken by a
   database account: the bootstrap super user must not share its name with a Keycloak account). With
   `internalAuthentication` the database super user of the previous step no longer logs in with its password (its
   API token keeps working, keep it as the break glass access).
3. `oidc.enabled: true`, `oidc.server: https://sso.example.com/realms/<realm>/` (trailing slash, checked by the
   chart), `oidc.clientSecret` (*secret*), `oidc.caCert` when the provider certificate comes from a private CA. Sync:
   `quay-app` pods roll. A wrong issuer or client secret is caught by `config-tool validate` when the new pods start:
   they crash loop (`oc logs deploy/<name>-quay-app`), the previous pods keep serving, the `QuayRegistry` turns
   `Available=False` and Argo CD stays `Progressing`; fix the values and sync again.
4. Any user of the realm allowed on the client gets a Quay account at first login (`FEATURE_USER_CREATION`): restrict
   the client in Keycloak when needed. Team synchronization is set per team in the UI or the API
   (`POST /api/v1/organization/<org>/team/<team>/syncing` with `{"group_name": "<group as sent in the claim>"}`);
   members are synchronized at each login of a user.
5. `internalAuthentication: false` keeps the database accounts and their passwords (external login button only), at
   the price of team synchronization and of password self registration being open.

### Verify the database certificates (`verify-full`)

The first sync uses `require` because the CA of the clusters does not exist before they are created. Then:

```bash
# crunchy (one root CA per operator) and percona (one root CA per cluster) | cloudnativedb (one CA per cluster)
oc get secret quay-db-cluster-cert -n quay-postgres -o jsonpath='{.data.ca\.crt}' | base64 -d   # cnpg: secret quay-db-ca
```

Put the PEM in `database.tls.caCert` (Vault + placeholder or values file), `database.tls.mode: verify-full`, sync.
The chart adds `sslrootcert` to `DB_URI` and `DB_CONNECTION_ARGS` (`/.postgresql/root.crt`, filled by the Quay image
from the `postgresql-client-certs` Secret), `extra_ca_cert_postgres-ca.crt` for Clair (`/var/run/certs/postgres-ca.crt`
in its connection strings). The `DB_URI` change makes the operator scale `quay-app` to zero while the upgrade job
runs (a few minutes): plan a maintenance window.

CA lifetimes: Crunchy signs with one root CA per operator (10 years, renewed in the last third of its validity:
refresh `caCert` then; the leaf certificates are renewed every year without any action); Percona signs with one root
CA per cluster on the same engine (concatenate the PEMs of the two clusters in `caCert`). CloudNativePG generates one
CA per cluster, valid `CERTIFICATE_DURATION` days (90 by default) and renewed 7 days before expiry: with
`verify-full` either raise `CERTIFICATE_DURATION` in the operator configuration, or refresh `caCert` after each
renewal; concatenate the PEMs of the two clusters in `caCert`. Otherwise keep `require` (traffic is encrypted, the
server is not authenticated).

### Backups and restore of the databases

Backups, point in time restore, in place restore (Crunchy, Percona) and the alerts watching the backup chain are
features of the database sub-charts: see the Procedures of
[cluster-crunchy](https://helm-repository.readthedocs.io/en/latest/charts/cluster-crunchy),
[cluster-cloudnativedb](https://helm-repository.readthedocs.io/en/latest/charts/cluster-cloudnativedb) and
[cluster-percona](https://helm-repository.readthedocs.io/en/latest/charts/cluster-percona), applied to the
`crunchy.cluster.list` / `cloudnativedb.cluster.list` / `percona.cluster.list` entries. Stop the registry first (`quay.stopped: true`,
sync: quay-app, clair-app and quay-mirror at zero) and end with `quay.stopped: false`. After a restore into a cluster
with a new name, point `database.quay.cluster` (and `clair`) to the new entry: `DB_URI` and the Clair connection
strings follow.

The registry bucket (layers) is not backed up by the chart: replicate or copy it (`aws s3 sync` without `--delete`)
at the rhythm of the database backups; Red Hat asks for the database and the bucket to be backed up together.

### Maintenance

| Need | How |
| --- | --- |
| Rotate a database password | Crunchy and Percona: change the value (Vault, hard refresh, sync: the pguser Secret and `DB_URI` change together), then at once `oc patch secret quay-db-pguser-quay -n quay-postgres --type json -p '[{"op":"remove","path":"/data/verifier"}]'` so that the operator recomputes the SCRAM verifier; the upgrade job started by the `DB_URI` change fails on authentication until then and is recreated by the operator. CloudNativePG: the `<cluster>-owner` Secret is reloaded and the role updated by `managed.roles`. In both cases the new `DB_URI` scales `quay-app` to zero during the upgrade job |
| Rotate `SECRET_KEY` | Allowed (sessions and tokens of the UI are invalidated). Never rotate `DATABASE_SECRET_KEY` |
| Quay update | Approve the InstallPlan in a maintenance window: the operator scales `quay-app` to zero while the database migrations run. Then pin `operator.subscription.version` / `csv` to the CSV that took your backups |
| Database operator update | Approve the InstallPlan: rolling restart, replicas first, then switchover |
| Resize a data volume | Increase `storageInstanceSize` of the cluster entry (StorageClass with volume expansion) |
| Stop the registry | `quay.stopped: true` |
| Change `parameters` of a cluster entry | Applied by the operator (Patroni / CloudNativePG reload, restart when the parameter needs it) |

### Monitoring

The Quay operator adds its own `ServiceMonitor` and rules (`QuayPodFrequentlyRestarting`) in the registry namespace
when `quay.components.monitoring` is managed. The database alerts (`CrunchyPostgres*`, `CloudNativePG*`) are rendered
by the sub-charts in the database namespace; the Percona clusters report to a PMM server instead. The Quay operator labels the registry namespace
`openshift.io/cluster-monitoring=true`, and so does the STARTX `project` chart on every namespace it creates,
including the database one: the platform Prometheus scrapes the `PodMonitor` and evaluates the `PrometheusRule` of
the databases, which Red Hat lists as unsupported for user objects. Give the databases a namespace created outside
the `project` sub-chart (`crunchy.project.enabled: false`) when they must stay with the user workload monitoring stack.
