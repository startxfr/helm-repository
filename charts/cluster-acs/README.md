# ![cluster-acs](https://helm-repository.readthedocs.io/en/latest/img/cluster-acs.svg "Cluster Chart : ACS") Cluster Chart : Advanced Cluster Security (Stackrox)
[![Artifacthub](https://img.shields.io/badge/ArtifactHub-STARTX_cluster--acs-8A2BE2.svg)](https://artifacthub.io/packages/search?ts_query_web=cluster+acs+startx)

This helm chart is used to deploy Advanced Cluster Security (ACS/Stackrox) handled by an operator to configure cluster security scanning and vulnerability management at the cluster level.

This chart is part of the [cluster-xxx startx helm chart series](https://helm-repository.readthedocs.io#cluster-helm-charts) that doesn't necessarily deploy pods but rather represent a cluster configuration state orchestrated by gitops tools like ArgoCD.

## Requirements and guidelines

Read the [startx helm-repository homepage](https://helm-repository.readthedocs.io) for
more information on how to use theses resources.

## Secured cluster services

`Central` alone does not secure any cluster: the `SecuredCluster` resource deploys Sensor, the admission
controller and Collector, and registers the cluster in a Central. It is disabled by default
(`acs.securedCluster.enabled: false`), so existing deployments render exactly as before.

The operator only starts the secured cluster services once the secret `cluster-registration-secret`
(Cluster Registration Secret, CRS, ACS 4.7+) or the init bundle secrets (`sensor-tls`, `admission-control-tls`,
`collector-tls`) exist in the namespace. `acs.securedCluster.registration.mode` selects how this chart provides it:

| Mode             | Usage                                  | Behaviour |
| ---------------- | -------------------------------------- | --------- |
| `job` (default)  | Central managed by this chart (hub)    | A Job waits for Central, generates a CRS through its API and creates `cluster-registration-secret` |
| `externalSecret` | Cluster registered in a remote Central | An `ExternalSecret` (External Secrets Operator) creates `cluster-registration-secret` from a CRS stored in a vault |
| `none`           | Secret provided by another process     | Nothing is created by the chart |

### Hub cluster (Central and SecuredCluster in the same namespace)

```yaml
acs:
  securedCluster:
    enabled: true
    # name of this cluster in ACS (required), cannot be changed once registered
    clusterName: hub
```

The registration Job:

1. waits for the Central admin password (secret `central-htpasswd`, key `password`, generated by the operator)
   and for the Central API (`https://central.<namespace>.svc:443/v1/ping`)
2. generates a CRS named `<clusterName>-<timestamp>`, optionally limited to `registration.job.maxRegistrations`
   cluster(s) (default `0`: unlimited, limit needs ACS 4.11+) and to a validity of `registration.job.validFor`
   (ex: `"31536000s"`, ACS 4.9+)
3. creates `cluster-registration-secret`, owned by the `Central` of the chart (deleted with it and its CA),
   and annotates the `SecuredCluster` (`startx.fr/cluster-registration`) so that the operator reconciles it
   immediately

The Job is idempotent and runs at every ArgoCD sync or helm upgrade:

- a secret it did not create (manual, ExternalSecret) or the init bundle secrets are never modified
- once the cluster is registered (secret `tls-cert-sensor` present), it exits without calling Central
- otherwise it replaces its secret when the CRS was issued by a previous instance of the `Central`, has
  expired, or was revoked or used up in Central

The Job is not a helm hook, `helm install` does not wait for Central. Its name ends with a hash of its pod
template, so a changed configuration creates a new Job instead of patching an immutable one. Its RBAC is
limited to reading the admin password and registration secrets, creating secrets, replacing
`cluster-registration-secret`, reading the `Central` and annotating this `SecuredCluster`. The admin password
is passed to `curl` on its standard input, not on its command line. The default image is
`registry.redhat.io/openshift4/ose-cli-rhel9:v4.21` (`registration.job.image`; with the internal registry enabled,
`image-registry.openshift-image-registry.svc:5000/openshift/cli:latest` follows the cluster release).

### Cluster registered in a remote Central (CRS stored in a vault)

Generate the CRS from the hub and store its content in the vault:

```bash
roxctl -e central-stackrox.apps.hub.example.com:443 central crs generate prod-1 -o prod-1-crs.yaml
sed -n 's/^  crs: //p' prod-1-crs.yaml | base64 -d > prod-1.crs
vault kv put secret/ocp/acs/prod-1 crs=@prod-1.crs
```

Then deploy only the secured cluster services on the remote cluster:

```yaml
externalSecretDefaults:
  secretStoreRef:
    name: vault            # ClusterSecretStore by default
acs:
  central:
    enabled: false
  securedCluster:
    enabled: true
    clusterName: prod-1
    centralEndpoint: central-stackrox.apps.hub.example.com:443
    clusterLabels:
      env: prod
    registration:
      mode: externalSecret   # or externalSecret.enabled: true, as in the other charts
      externalSecret:
        remoteRefs:
          crs:
            key: ocp/acs/prod-1
            property: crs
```

With `acs.central.enabled: false`, `acs.securedCluster.centralEndpoint` is required
(`central.<namespace>.svc:443` for a Central deployed in the same namespace by another release).

The `job` mode can also register a remote cluster: the Job then calls `acs.securedCluster.centralEndpoint`
(or `registration.job.centralEndpoint`) with the admin password read from the secret set in
`registration.job.adminPasswordSecret`. The Job does not verify the Central certificate (internal ACS CA),
prefer the `externalSecret` mode when the API is reached outside the cluster network.

### Configuration

| Key | Default | Description |
| --- | ------- | ----------- |
| `acs.securedCluster.enabled` | `false` | Deploy the `SecuredCluster` |
| `acs.securedCluster.hooked` | `false` | Deploy the `SecuredCluster` in the ArgoCD `PostSync` phase (always the case when `acs.central.hooked` is true) |
| `acs.securedCluster.name` | `stackrox-secured-cluster-services` | Name of the resource, must differ from `acs.central.name` |
| `acs.securedCluster.clusterName` | required | Name of this cluster in ACS, cannot be changed once registered |
| `acs.securedCluster.centralEndpoint` | `""` | Central endpoint (`host:port`), empty for the Central of the same namespace (required when `acs.central.enabled` is false) |
| `acs.securedCluster.clusterLabels` | `{}` | Labels of this cluster in ACS |
| `acs.securedCluster.admissionControl.enforcement` | `Enabled` | Policy enforcement by the admission controller |
| `acs.securedCluster.admissionControl.failurePolicy` | `Ignore` | Webhook failure policy (`Ignore` or `Fail`) |
| `acs.securedCluster.perNode.collection` | `CORE_BPF` | Collector collection method (`CORE_BPF` or `NoCollection`) |
| `acs.securedCluster.perNode.taintToleration` | `TolerateTaints` | Run Collector on tainted nodes too |
| `acs.securedCluster.auditLogs` | `Auto` | Kubernetes audit logs collection |
| `acs.securedCluster.scanner` | `AutoSense` | Local scanner (not deployed when Central runs in the same namespace) |
| `acs.securedCluster.scannerV4` | `Default` | Local Scanner V4 |
| `acs.securedCluster.spec` | `""` | Additional `SecuredCluster` spec (YAML string or map) merged over the generated one |
| `acs.securedCluster.registration.mode` | `job` | `job`, `externalSecret` or `none` |
| `acs.securedCluster.registration.job.*` | | `image`, `centralEndpoint`, `adminPasswordSecret`, `maxRegistrations`, `validFor`, `timeoutSeconds`, `ttlSecondsAfterFinished` |
| `acs.securedCluster.registration.externalSecret` | `{}` | `secretStoreRef`, `refreshInterval`, `remoteRefs`, `data`, `dataFrom`, `template` (key `crs` required) |
| `externalSecretDefaults` | | Default `apiVersion`, `refreshInterval` and `secretStoreRef` of the ExternalSecret |

With `acs.infra: true`, Sensor, the admission controller and the local scanners run on infra nodes
(Collector keeps running on every node).

Empty values (`""`) leave the corresponding field to the operator default. Any other field of the
`SecuredCluster` spec can be set with `acs.securedCluster.spec`, ex:

```yaml
acs:
  securedCluster:
    spec: |
      sensor:
        resources:
          requests:
            cpu: 500m
```

### Deployment order and re-registration

With ArgoCD, the Job RBAC is applied in wave `0` (with Central), the Job in wave `1` and the `SecuredCluster`
in wave `2`. When Central or the SecuredCluster is hooked, the Job and the `SecuredCluster` both run in the
`PostSync` phase, after Central. `acs.securedCluster.hooked` only applies to ArgoCD: with helm alone the
`SecuredCluster` stays a regular release resource (a helm hook could not be upgraded). With helm alone and
`acs.central.hooked: true`, do not use `--wait-for-jobs`: helm would wait for the Job before creating Central.
Add `/metadata/finalizers` of `SecuredCluster` to the Application `ignoreDifferences`
(see [examples/argocd](https://github.com/startxfr/helm-repository/tree/devel/charts/cluster-acs/examples/argocd)).

Once registered, Sensor uses its own certificates (secrets `tls-cert-*`, deleted with the `SecuredCluster`):
the CRS is only used again when the `SecuredCluster` is re-created. A CRS limited with `maxRegistrations`
(or `roxctl --max-clusters`) is revoked by Central once used. In `job` mode, the next run of the Job replaces
a revoked, expired or obsolete CRS while the cluster is not registered. To force a new registration, delete
the secret `cluster-registration-secret` and run the Job again (ArgoCD sync, or `helm upgrade` once the
previous Job has been removed after `ttlSecondsAfterFinished`). In
`externalSecret` mode, update the CRS stored in the vault. CRS generated by the Job are listed with
`roxctl central crs list`.

## ArgoCD deployment

### Deploy via ArgoCD Application

Deploy `cluster-acs` using three dedicated ArgoCD Applications - one per concern - all sharing the same AppProject.
The ACS operator installs in the shared `openshift-operators` namespace. The `Central` CR deploys in `startx-acs`:

```bash
git clone https://gitlab.com/startx1/helm.git
cd helm-repository/charts/cluster-acs/examples/argocd/
oc apply -k .
```

The automated sync policy ensures ArgoCD reconciles each concern independently whenever the chart or values drift from the desired state.
